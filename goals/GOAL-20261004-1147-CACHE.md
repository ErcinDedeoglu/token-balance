# GOAL-20261004-1147-CACHE: Shared snapshot cache for concurrent tb panes

## Intent

A developer running `tb` in several panes at once causes one vendor fetch per pane per minute, so concurrent `tb` panes share one snapshot cache with a single writer and readers render the cache instead of polling vendors themselves.

## Problem

The board is multi-pane by design but has no coordination: each `tb` process polls every vendor on its own 60s timer, so running it twice hits each vendor twice per minute and running it ten times hits each vendor ten times per minute. Muse is worse: each boot burns at least one Everyday sandbox request even when remaining is already known (user discussion 2026-10-04).

## Outcome

N `tb` panes share one snapshot file. The oldest live pane is the writer; other panes read the file and stop polling vendors themselves. Reader panes skip Muse. The writer persists its snapshots so only the first pane after a cold start burns the Muse request. No daemon, no server, no `tb serve` mode, no cross-process locking.

## Scope

### In

- Single-writer snapshot cache file shared by concurrent `tb` panes on one machine
- Writer election: the oldest live pane writes; readers render the cache and do not poll vendors
- Readers skip Muse entirely; the writer persists its snapshots on a cadence so a later boot reads the cache instead of burning another Muse request
- Cache format holds `Vec<ProviderSnapshot>` with the same status shapes the domain already uses (`Available`, `Error` with stale, `NotConfigured`, `Unsupported`)
- Failure/edge behavior: writer exits (next-oldest pane takes over), cache file missing or unreadable (pane falls back to live polling), stale cache (age shown like today's `stale` footer, never a numeric `0%`)
- Recorded tests for writer election, reader skip, stale fallback, and corrupt-cache fallback
- Design record in `docs/design/` for the cache location, format, and writer-election rule

### Out

- Do not add a `tb serve` subcommand or any daemon, HTTP server, socket, or client protocol
- Do not add cross-process locking, lockfiles, or filesystem-watch refresh
- Do not change adapter fetch logic or remaining mappers
- Do not add statusline, `--json`, `--theme`, `--once`, or Prometheus
- Do not persist view or sort to disk or `accounts.toml`
- Do not mix live adapters with `--fixture`; `--fixture` panes never read or write the live cache
- Do not store credentials, tokens, cookies, or credential file contents in the cache file
- Do not change the 7-row card anatomy, card `hero_window`, or table packing

## Assumptions

- Cache lives under `{HOME}` (same process home `Credentials` already uses), so panes as the same user share it
- Writer election uses process liveness/age observable from the filesystem, not a lock
- Reader panes already have `accounts.toml` rows for display names; the cache only supplies statuses
- One boot of `tb` still fetches Muse once when the cache has no usable snapshot (cold start)

## Acceptance criteria

### Must

- [ ] **AC-1** Given two `tb` panes open on the same machine, when both pass a 60s boundary, then each vendor endpoint receives one request, not two.
      Verify plan: Run two live panes, observe vendor-side request counts (or a counting stub) across one timer boundary; expect one hit per vendor. Control: a single pane also shows one hit per vendor.
- [ ] **AC-2** Given the writer pane quits, when the next 60s boundary passes, then a remaining pane takes over and vendor fetches continue exactly once per boundary.
      Verify plan: Kill the oldest pane, observe the next boundary still produces one hit per vendor and the board keeps refreshing. Failure control: with no panes left, no fetches happen.
- [ ] **AC-3** Given the cache file is missing or corrupt, when a pane starts, then it falls back to live polling and paints live data instead of crashing or showing empty `error` rows.
      Verify plan: Delete/corrupt the cache, launch `tb`, and observe live rows appear; restore and observe the cache path resumes.
- [ ] **AC-4** Given a usable cached Muse snapshot, when a second pane boots, then it does not issue a Muse request and shows the cached Muse row.
      Verify plan: Boot pane one, confirm one Muse request; boot pane two, observe no second Muse request while the Muse row still renders. Control: cold start with no cache still fetches Muse once.

## Risks

- Filesystem-based writer election without locking can briefly elect two writers; last-writer-wins keeps this benign but the implementation must tolerate it
- A stale cache must never render as `0%` remaining for `NotConfigured` / `Unsupported` rows
